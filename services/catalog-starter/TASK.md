# Шаг 3. Команды, валидация и коды ошибок

## Что нужно сделать

Каталог умеет только читать и создавать. Добавь две команды:

```
PATCH /products/{id}/price    {"price": 1490.00}
PATCH /products/{id}/stock    {"delta": 7}     поступление
PATCH /products/{id}/stock    {"delta": -3}    списание
```

Обе отвечают обновлённым товаром. Правила отказов:

| ситуация | код | откуда берётся отказ |
|---|---|---|
| цена не число, отрицательная или не пришла | 400 | модель pydantic в роутере, в теле поле `errors.price` |
| `delta` не пришла | 400 | то же, поле `errors.delta` |
| `delta` нулевая | 400 | смысл команды, вход формально корректен: ошибка из класса `Product` |
| списание уводит остаток в минус | 409 | состояние товара: сейчас так нельзя |
| товара с таким id нет | 404 | уже реализовано, ломать не нужно |

Разница между 400 и 409 - здесь главное. 400 - «запрос неправильный, его нельзя
даже начать выполнять». 409 - «запрос правильный, но текущее состояние не даёт его
выполнить»: завтра товар довезут, и тот же самый запрос пройдёт.

## Где править

`# TODO шаг 3` стоит в трёх файлах `catalog_starter/product`: `model.py`,
`service.py`, `router.py`.

Обработчики в `catalog_starter/problem.py` трогать не нужно - они уже переводят
ошибки в ответы и служат образцом. Посмотри на них первыми: по классам ошибок
видно, какая каким кодом обернётся, и это подсказывает, что поднимать из класса
`Product`. Пропавшее поле в JSON pydantic ловит сам: обязательное поле без
значения по умолчанию даёт ошибку `missing` с именем поля.

## Как проверить себя

```bash
python -m pytest -q
```

Красный `tests/test_change_api.py` - семь проверок, по одной на строку таблицы
плюс успешные сценарии. Тело ответа на 400 обязано называть поле: тест смотрит в
`errors.price` и `errors.delta`. Остальные тесты должны остаться зелёными.

## На что посмотреть по дороге

- Неудачное списание не должно менять остаток - тест это проверяет отдельно.
  Если остаток «уполз», значит состояние поменяли до проверки. Обрати внимание:
  объект в сессии SQLAlchemy меняется в памяти, а исключение откатывает
  транзакцию - так что порядок «проверить, потом менять» важен вдвойне.
- PATCH против PUT: PUT заменяет ресурс целиком, а мы меняем одно поле.
- 422 вместо 400 - FastAPI по умолчанию отвечает именно 422; посмотри в
  `problem.py`, как это переопределено, и в материале, почему на практике чаще
  останавливаются на 400.
- Ошибка с данными (`OutOfStockError` с `requested` и `available`) против ошибки
  без них (`InvalidError`): первую обработчик разбирает, когда нужны подробности
  в `detail`, вторую - когда важен только вид.
